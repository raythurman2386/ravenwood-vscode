# VS Code Theme Building

A VS Code theme extension ships JSON files that map every UI surface and syntax token to colors. This skill covers the reusable architecture patterns for building one: palette design, modular token mapping, dynamic (runtime) vs static (build-time) theme generation, testing, and publishing to both Marketplaces.

This repo (Ravenwood) is a production example of every pattern below. For project-specific conventions, color tables, and exact build commands, see the sibling `ravenwood` skill at `.agents/skills/ravenwood/SKILL.md`.

## When to Use

- Building a new VS Code theme extension from scratch
- Adding workbench color keys, syntax rules, or semantic token mappings
- Setting up dynamic theme regeneration (user-configurable options)
- Adding static theme variants (fixed artistic themes with no config)
- Auditing workbench color key coverage against the VS Code reference
- Publishing to VS Code Marketplace and/or Open VSX

Don't use for: porting the Ravenwood color scheme to non-VS-Code apps — use the Hermes `ravenwood-theme` porting skill instead.

## Architecture

### Core Pattern

```
Palette (color source) → Token Mappers → Theme JSON → package.json contributes.themes
```

Separate the *palette* (raw colors) from the *token mappers* (functions that map palette colors to VS Code color keys). This lets you:

- Swap palettes without changing token mapping logic
- Generate multiple themes from the same mapping functions
- Share token mapping logic between dynamic (runtime) and static (build-time) themes

### Recommended Module Layout

```
src/
├── interface.ts           TypeScript interfaces: Palette, Configuration, ThemeData, SyntaxRule
├── themeData.ts           Pure ThemeData builder (shared by runtime + build-time)
├── utils.ts               Runtime: config detection, file writing, regeneration
├── semantic.ts            LSP semantic token colors (getSemantic + getSemanticFromPalette)
├── hook/
│   └── generateThemes.ts  Build-time script → writes themes/*.json (dynamic + static)
├── palette/
│   ├── index.ts           getPalette() — dispatches by variant × contrast
│   ├── dark/
│   │   ├── foreground.ts   fg + accent colors (shared across contrast levels)
│   │   └── background/{soft,medium,hard}.ts  bg0–bg5, shadow
│   ├── light/
│   │   ├── foreground.ts
│   │   └── background/{soft,medium,hard}.ts
│   └── realms/            Static theme palettes (one file per fixed theme)
├── workbench/
│   ├── index.ts           getWorkbench() — dispatches by style
│   ├── common.ts          Selection, cursor, diagnostic, variant color helpers
│   ├── base.ts            ~95% shared token map (~971 keys)
│   ├── material.ts        Material style (default — no overrides)
│   ├── flat.ts            Flat style — overrides list/sidebar/tab backgrounds
│   └── highContrast.ts    High-contrast — darker activity bar / sidebar
└── syntax/
    ├── index.ts           getSyntax() — dispatches by italic setting
    ├── default.ts         Default (upright) TextMate rules
    └── italic.ts          Italic variant — keywords + comments in italic
```

### Dynamic vs Static Themes

**Dynamic themes** regenerate at runtime when the user changes settings:

- Entry points: `index-client.ts` (desktop), `index-web.ts` (web)
- `activate()` registers an `onDidChangeConfiguration` listener
- On config change → `getThemeData(config)` → write `themes/*.json` → VS Code auto-reloads
- The `ThemeData` builder must be pure (no `vscode` imports) so it runs at build time too

**Static themes** are fixed artistic statements with no user config:

- No `main`/`browser`/`activationEvents` needed — just JSON files in `contributes.themes`
- Generated at build time from a palette + fixed Configuration
- Use the same token mappers (workbench, syntax, semantic) with a hardcoded config
- In this repo: the 8 realm themes (Asgard, Vanaheim, Alfheim, Svartalfheim, Nidavellir, Jotunheim, Muspelheim, Helheim) are static themes generated by `generateThemes.ts` alongside the dynamic Dark/Light themes

### Build Pipeline

```
npm run compile    # clean → tsc → generateThemes.js → themes/*.json
npm run package    # vsce package → .vsix
```

`themes/` is a build artifact — gitignore it. `generateThemes.ts` regenerates from source on every compile. The script MUST NOT import the `vscode` module (it runs under plain Node).

## Palette Design

### The 27-Key Palette Interface

```typescript
interface Palette {
  // Backgrounds (11 keys)
  bg0: string; bg1: string; bg: string; bg2: string;
  bg3: string; bg4: string; bg5: string;
  grey0: string; grey1: string; grey2: string;
  shadow: string;
  // Foreground + accents (16 keys)
  fg: string;
  red: string; orange: string; yellow: string;
  green: string; aqua: string; blue: string; purple: string;
  dimRed: string; dimOrange: string; dimYellow: string;
  dimGreen: string; dimAqua: string; dimBlue: string; dimPurple: string;
  badge: string;
}
```

### Design Rules

- **Background gradient**: bg0 (darkest) → bg5 (lightest) for dark themes; reverse for light. Smooth lightness increase at each step.
- **Backgrounds should have a tint** — not neutral grey. A green-tinted dark theme reads as "forest", a neutral grey reads as "generic".
- **Foreground should not be pure white/black** — warm beige (#e8d5b7) on dark, cool slate (#3d4c53) on light gives personality.
- **Dim variants** for every accent — use for secondary UI, not primary semantic meaning. Dim = darker AND less saturated than the parent.
- **Contrast levels adjust backgrounds only** — foreground and accent colors stay the same across soft/medium/hard.
- **Shadow alpha differs by variant** — dark themes use higher alpha (e.g. #00000070 = 44%), light themes use lower (e.g. #3c474d20 = 12%).
- **Badge is the hero accent** — use for notification badges, primary CTAs, success states.

Use `satisfies Partial<Palette>` on each palette file so misspelled keys fail at compile time:

```typescript
export default {
  fg: '#e8d5b7',
  red: '#e67e80',
  // ...
} satisfies Partial<Palette>;
```

### Adding a Static Theme Palette

1. Create `src/palette/realms/<name>.ts` exporting a full `Palette` object
2. Add the realm to the `realms` array in `src/hook/generateThemes.ts` with `isDark: true/false`
3. Add the theme to `contributes.themes` in `package.json` with the correct `uiTheme` (`vs-dark` or `vs`)
4. Run `npm run compile` to generate the theme JSON
5. Verify the theme loads in VS Code (Preferences → Color Theme)

## Workbench Color Keys

### Coverage Audit

VS Code exposes ~910 official core workbench color keys (as of VS Code 1.99.x). A complete theme covers all of them. Audit against the official reference at `https://code.visualstudio.com/api/references/theme-color`.

Key categories: editor, terminal, activity bar, sidebar, status bar, tabs, lists/trees, inputs, buttons, dropdowns, notifications, command center, SCM graph, gauge, markdown alerts, agent session, terminal symbol icons, bracket pair guides, indent guides, inline edit, merge editor, multi-cursor, radio, diff editor, charts, quick picker, notebook, testing, welcome page, search editor, suggest widget, peek view, debug, minimap, banner, settings.

### Style Dispatch Pattern

Share ~95% of the token map in `base.ts`, then each style overrides only what it needs:

```typescript
// base.ts — shared tokens
export function getBaseWorkbenchTokens(palette, config, variant): Record<string, string> {
  return { /* ~950 keys */ };
}

// material.ts — default style, no overrides
export function materialWorkbench(palette, config, variant) {
  const tokens = getBaseWorkbenchTokens(palette, config, variant);
  return applyHighContrastFlag(palette, config, tokens);
}

// flat.ts — override list/sidebar/tab backgrounds
export function flatWorkbench(palette, config, variant) {
  const tokens = getBaseWorkbenchTokens(palette, config, variant);
  return { ...tokens, ...flatOverrides };
}
```

### Variant-Dependent Colors

Some colors depend on dark vs light (terminal ANSI, validation backgrounds, highlight opacity). Extract these into a `getWorkbenchVariantColors(palette, isDark)` helper rather than branching inline.

## Syntax Rules (TextMate)

### Scope Mapping Convention

| Semantic role   | Palette color | Example scopes                          |
|-----------------|---------------|-----------------------------------------|
| Keyword         | red           | `keyword`, `storage.type`               |
| Function        | green         | `entity.name.function`                  |
| String/constant | yellow        | `string`, `constant.numeric`             |
| Type/class      | aqua          | `entity.name.type`, `support.class`      |
| Operator        | orange        | `keyword.operator`                       |
| Variable        | blue          | `variable`, `variable.parameter`         |
| Special/builtin | purple        | `constant.language`, `variable.language`|
| Comment         | grey0         | `comment`                                |

### Default + Italic Sync

Maintain two parallel rule arrays: `default.ts` (upright keywords) and `italic.ts` (italic keywords). Every rule in one must exist in the other (with the italic variant adding `fontStyle: "italic"` to keyword/declaration rules). This is the #1 source of regressions — always update both files together.

### Scope Safety Rules

1. **Always include the language suffix** — `entity.name.class.scala`, NOT `entity.name.class`. A bare scope overrides ALL languages.
2. **Check for shadowed rules** — if two rules match the same scope, the first one wins. Check for existing overlaps before adding new ones.
3. **Use language-specific scopes for expanded coverage** — e.g., `keyword.control.import.js`, `entity.name.type.module.ts`

## Semantic Tokens (LSP)

Map LSP token types to palette colors using language-scoped keys:

```typescript
export function getSemanticFromPalette(palette: Palette): Record<string, string> {
  return {
    'function:rust': palette.green,
    'struct:rust': palette.aqua,
    'variable:python': palette.fg,
    'class:java': palette.aqua,
    // ...
  };
}
```

Common token types: `class`, `function`, `method`, `variable`, `parameter`, `property`, `type`, `struct`, `enum`, `enumMember`, `module`, `namespace`, `typeParameter`, `decorator`, `macro`, `lifetime`, `trait`, `selfKeyword`.

The `getSemanticFromPalette(palette)` pattern lets both dynamic and static themes share the same semantic mapping — the dynamic path wraps it with `getSemantic(config, variant)` that resolves the palette first.

## Configuration Options

User-configurable options live under `ravenwood.*` in `contributes.configuration.properties`. When adding a new option, update ALL of these:

1. `package.json` — add to `contributes.configuration.properties`
2. `src/interface.ts` — add to `Configuration` interface
3. `src/utils.ts` — read it in `getConfiguration()`
4. `src/utils.ts` — compare it in `isDefaultConfiguration()`
5. `src/hook/generateThemes.ts` — include its default value for build-time

Common options: contrast levels (soft/medium/hard), workbench style (material/flat/high-contrast), cursor color, selection color, italic keywords/comments, diagnostic opacity, high contrast border.

## Testing

### Test Suite Structure

| Suite            | What it checks                                              |
|------------------|------------------------------------------------------------|
| Structural       | Theme JSON has correct top-level keys, hex validation, workbench key coverage count, dark/light parity |
| Palette          | Color values match documented specs, dim variants exist and are darker+less saturated than parents |
| Contrast (WCAG)  | Primary text meets AAA (≥7), grey text meets AA-large (≥3), badge contrast, foreground tint (not pure white/black), background tint (not neutral grey), background gradient smoothness |
| Sync             | `default.ts` and `italic.ts` have matching language coverage and scopes |
| Scope-safety     | All language-specific scopes have a language suffix (no overbroad scopes) |
| Build-combos     | All N configuration combinations produce valid theme output |

### Test Runner

Use Node's built-in test runner (`node:test`) with `tsx` for TypeScript:

```bash
node --import tsx --test test/*.test.ts
```

No external test framework needed. Wire into CI via GitHub Actions.

## Publishing

### VS Code Marketplace

1. Get a Personal Access Token from `https://dev.azure.com` (Publisher account required)
2. `vsce package` produces a `.vsix`
3. `vsce publish` or set up a GitHub Actions workflow with `HaaLeo/publish-vscode-extension`

### Open VSX

1. Get a token from `https://open-vsx.org`
2. Use `ovsx publish` or the `HaaLeo/publish-vscode-extension` action with `registryUrl: https://open-vsx.org`

### Release Workflow

This repo uses a tag-triggered GitHub Actions workflow (`.github/workflows/stable_release.yml`) that:
1. Runs tests
2. Bumps version
3. Builds `.vsix`
4. Publishes to Marketplace + Open VSX
5. Creates a GitHub Release with auto-generated notes

### Static-Only Themes

If an extension ships only static theme JSONs (no runtime code, no `main`/`browser`/`activationEvents`), it still needs `engines.vscode` and `contributes.themes` in `package.json`. No TypeScript compilation needed — just JSON files.

## Common Pitfalls

1. **Missing italic.ts sync** — every syntax rule added to `default.ts` must also go to `italic.ts`. The #1 source of regressions.

2. **Overbroad scopes** — scope strings must include the language ID suffix (e.g., `entity.name.class.scala`). A bare `entity.name.class` overrides ALL languages.

3. **Invalid hex in template literals** — check for stray `}` characters inside backtick strings. These produce invalid hex like `#da636280}` that VS Code silently rejects.

4. **Forgetting `npm run compile:themes`** — the `themes/*.json` files are build artifacts. After palette or workbench changes, regenerate them or the extension ships stale themes.

5. **Importing `vscode` in build-time code** — `generateThemes.ts` runs under plain Node. The `ThemeData` builder must be pure (no `vscode` imports). Keep it in a separate module (`themeData.ts`), not in `utils.ts`.

6. **Both variants** — when changing palette colors, update dark AND light together. A change to one without the other creates visual inconsistency.

7. **Deprecated VS Code keys** — VS Code renames and removes theme keys between versions. Audit against the current official reference. Shipping deprecated keys wastes space and can mask missing current keys.

8. **Variant dispatch fallbacks** — variant-dispatching functions should `throw` on unknown variants, not silently fall back to light. Silent fallbacks hide bugs.

9. **Not testing config combinations** — if the theme has N configurable options, test that all N combinations produce valid output. A 12-option theme has 50 meaningful combinations.

10. **Shipping themes/ in git** — `themes/*.json` are build artifacts. Gitignore them and regenerate on compile. This prevents stale themes from being merged.

## Verification Checklist

- [ ] `npm run compile` succeeds (tsc + theme generation)
- [ ] `npm run lint` passes
- [ ] All tests pass (structural, palette, contrast, sync, scope-safety, build-combos)
- [ ] Syntax rules added to BOTH `default.ts` and `italic.ts`
- [ ] Semantic tokens use language-scoped keys (e.g., `function:rust`, not bare `function`)
- [ ] No overbroad scopes (all scope strings end with a language suffix)
- [ ] No stray `}` in template literals (check hex color values)
- [ ] Workbench key count matches the official VS Code reference
- [ ] Dark and light have identical workbench key sets
- [ ] Copyright header on any new source file
- [ ] `themes/*.json` regenerated and not committed (gitignored)
- [ ] `npm run package` produces a valid `.vsix`
